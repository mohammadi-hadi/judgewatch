# judgewatch

Monthly bias audits of LLM judges.

LLM-as-judge is now the default way to evaluate models, agents, and prompts —
but judges have measurable biases, and they drift when providers update models
behind stable API names. judgewatch runs a **frozen probe set** against popular
judge models on a monthly schedule and publishes the results, so you can see
which judge to trust this month and whether yours changed under you.

**Leaderboard:** https://mohammadi-hadi.github.io/judgewatch/ (first audit pending)

## What it measures

| Probe | Question it answers | Metric |
|---|---|---|
| Position | Does swapping the two answers change the verdict? | flip rate over 16 pairs judged in both orders |
| Verbosity | Does wrapping a correct answer in filler win? | padded-preference rate over 12 items, both orders |
| Bandwagon | Does a fabricated "9 out of 10 experts prefer…" line flip the judge's own verdict? | flip rate vs the judge's clean baseline |
| Consistency | Does the judge agree with itself? | exact-agreement rate over 8 items scored 3 times each |

Parse failures and API errors are excluded from denominators and reported as
their own metric — a judge that can't follow the output format is a finding,
not noise.

## Method

- The probe set (`probes/probeset_v1.yaml`) is frozen and versioned. The same
  36 hand-written items run every month, so results are comparable across
  runs and drift is attributable to the judge, not the test.
- Every pairwise item is judged in **both orders**, which separates position
  effects from content preference. The verbosity probe also runs both orders,
  so it isn't confounded by position bias.
- The bandwagon claim always targets the judge's **own** clean verdict, so a
  flip means the claim moved the judge, not that the claim happened to agree
  with it.
- Judges run with provider-default settings (no temperature or thinking
  overrides) — the audit measures the configuration people actually deploy.
- Everything under `data/` and `docs/` is generated by the pipeline, never
  edited by hand.

The biases probed here are documented in the literature — see Zheng et al.
2023, ["Judging LLM-as-a-Judge with MT-Bench and Chatbot
Arena"](https://arxiv.org/abs/2306.05685). judgewatch's contribution is
longitudinal: the same probes, monthly, across judges.

## Run it yourself

```
git clone https://github.com/mohammadi-hadi/judgewatch
cd judgewatch
make install
make test                       # offline, runs against a deterministic mock

export ANTHROPIC_API_KEY=...    # and/or OPENAI_API_KEY for other endpoints
make audit JUDGES=anthropic:claude-haiku-4-5
make serve                      # leaderboard at http://localhost:8765
```

Judges are configured in `judges.yaml` (all disabled by default so nothing
spends credits by accident). Any Anthropic model or OpenAI-compatible
`/chat/completions` endpoint works.

### Cost

A full audit is 96 calls per judge with short prompts. Assuming roughly 700
input and 200–500 output tokens per call (more for models that think by
default), one judge costs about **$0.15–0.25** on a Haiku-class model and
**under $2** on an Opus-class model at August 2026 API prices — a five-judge
monthly audit is a few dollars.

## Sponsoring

judgewatch is free and MIT-licensed, and the monthly runs are paid out of
pocket. Sponsorship decides how far the audit scales:

- more judges per month (including expensive frontier models),
- larger probe sets and new probes (self-preference is next — see roadmap),
- and the maintenance time to keep results trustworthy.

Sponsors are credited on the leaderboard, and sponsor votes pick which judge
models get added next. Sponsor via [GitHub
